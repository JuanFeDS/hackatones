# Sesión — 2026-08-22

## Sesión 1

### Tema principal
Deploy del chat (Chainlit + Claude Agent SDK) del analista financiero de Quick Logística a un hosting real (Render, Docker) con dominio público, y resolución iterativa de varios bugs de arranque/conexión en local y en producción.

### Decisiones tomadas
- Deploy en **Render** (Web Service, Docker), no GitHub Pages — GH Pages es estático y no puede correr el backend Python+Node que necesita el chat (spawnea el CLI de Claude Code como subproceso y necesita la API key como secreto).
- Repo **privado** en GitHub (`JuanFeDS/hackaton_claude`) por defecto — contiene datos financieros reales pseudonimizados (61MB, entra sin Git LFS).
- Chat sin trazas visibles en la UI (pedido explícito del usuario, dos veces) — se separó un system prompt específico para chat (`build_chat_system_prompt`) que mantiene el rigor interno (planear→ejecutar→verificar) pero solo expone la conclusión final en tono conversacional, no narrado paso a paso.
- En vez del punto de carga genérico de Chainlit, un mensaje de estado dinámico y amigable (sin nombres técnicos de herramientas ni JSON) que va cambiando mientras el agente trabaja y termina convirtiéndose en la respuesta final.

### Trabajo realizado
- Corregidos dos bugs de arranque local del chat: `chainlit run -w` (watch mode) se recargaba solo por la escritura de la caché parquet; y `get_bench_tools()` no tenía lock ni caché en xlsx de nómina/ausencias, generando un "thundering herd" cuando el navegador reintentaba la conexión antes de que terminara la carga (~46s sin caché).
- Agregada caché parquet a `load_nomina`/`load_ausencias` (igual que `load_ledger`) en `data/quick_bench_toolkit.py`.
- Agregado `threading.Lock` real (double-checked locking) a `get_bench_tools()` en `agent/sdk_tools.py`.
- La precarga de datos en `app.py` pasó a correr en un hilo de fondo (no bloquea el import del módulo, para que Chainlit abra el puerto HTTP de inmediato).
- Creados `Dockerfile`, `.dockerignore`, `render.yaml` para el deploy.
- `git init`, limpieza de archivos sueltos de debug (`_*.txt`, logs, `.files/`, `charlas/` como submódulo embebido), `.gitignore` actualizado.
- Repo creado y pusheado a `github.com/JuanFeDS/hackaton_claude` (privado).
- Deploy manual en Render (Web Service, no Blueprint) → `https://hackaton-claude.onrender.com`.
- Iteración de fixes en producción a partir de logs reales de Render:
  - El CLI de Claude Code rechaza `--dangerously-skip-permissions` corriendo como root → usuario no-root (`appuser`) agregado al Dockerfile.
  - `Control request timeout: initialize` → `CLAUDE_CODE_STREAM_CLOSE_TIMEOUT=180000` seteado a mano en el dashboard de Render (el servicio se creó manual, no vía Blueprint, así que `render.yaml` no se aplica solo).
  - Causa raíz real del cuelgue: el parseo pesado (CSV 255k filas + 6 xlsx) corriendo en el hilo de fondo acaparaba el GIL bajo el CPU muy limitado del plan free de Render, atrasando los heartbeats del socket de Chainlit → el navegador asumía desconexión y reintentaba sin que ningún intento llegara a completar. Fix definitivo: **commitear la caché parquet ya generada** (`data/.cache/*.parquet`, ~6MB) al repo, para que en runtime solo se lea parquet (~1-2s) y nunca se vuelva a parsear el CSV/xlsx.
  - Agregada una guarda en `handle_message` para no crashear feo si `connect()` falla (mensaje amigable pidiendo refrescar).
- Actualizado `docs/brief.md` con la arquitectura final completa (pivote sin código, postmortem del bug de arranque, resultados del leaderboard, notas de deploy).

### Conclusiones
- El CPU compartido/throttled del plan free de Render es una restricción real para esta arquitectura (Python + subproceso Node) — subir timeouts no alcanza si hay trabajo CPU-bound compitiendo por el GIL; había que eliminar ese trabajo en runtime (caché commiteada).
- El Claude Agent SDK trae un binario nativo del CLI bundleado en el paquete pip para Linux (`_bundled/claude`) — el `npm install -g @anthropic-ai/claude-code` del Dockerfile terminó siendo innecesario (se dejó igual, sin riesgo).
- El chat quedó funcional en producción tras la secuencia: usuario no-root → timeout más alto → caché commiteada (esta última fue la que realmente lo arregló).
